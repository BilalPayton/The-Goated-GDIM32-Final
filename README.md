### Group Devlog
One design pattern we used in our project is Inheritance and Polymorphism for our Items and NPCs. They can be found used with the parent classes Items and NPCMultipleBranches used for our child classes Beans and JoeDialogue. The Beans class inherits all of the aspects from the Item class that all item needs no matter their function, such as being able to be picked up when clicked and having their own unique data, but Polymorphism comes into play when an item does something completely different from another item when used. For example, our Beans class overrides the OnMouseClick() method inherited from the Item parent class and heals the player for 10 health when clicked, something that does not happen with our other item Keys, which does not heal the player for any health when picked up. This is useful because it allowed us to avoid coding two separate classes for our Beans and Keys Items that would have mostly identical code to each other which would be redundant and a waste of time. For our NPCS Joe and CarDealer, they inherit from the NPCMultipleBranches parent class to inherit all the aspects of talking to them such a showing and running their dialogue and showin the player options. Polymorphism is used here because the NPCS both show different dialogue and response options to the player depending on which one you talk to, and they also override a method in the parent class CheckForQuestItem(). Joe for example overrides this method to specifically check that the player obtained his beans, in which if the player has, he will run different dialogue from what the player saw when they didn't have the beans. Although our CarDealer NPC doesn't utilize this in the same way, it is great practice for the game to scale NPCS well if we wanted to add more of them and have them check for specific items that the player has. This design pattern was useful in our project because it easily allowed as to add more NPCs needed to our game and give them unique dialogue without coding up two separate classes that would almost have entirely identical code.

Another design pattern we used in our project is the Finite State Machine Pattern for our ZombieNPC class. We used an enum ZombieState to give the Zombies a Wandering and a Chasing state so code intended for these states don't overlap and only run one set of code at a time. In the ZombieNPC class' UpdateState() method, we used a boolean member variable hasLineOfSightToPlayer to check if the Zombies can see the player, if they do then the enum member variable _state is assigned to Chasing and if they don't then it is assigned to Wandering. The class' other method RunState() then checks the _state member variable and runs code depending on what it is assigned to. If _state is assigned to Wandering, the method RunWanderState() is called which runs code for the Zombies wandering around the map. If _state is assigned to Chasing, the method RunChaseState() is called which runs code for the Zombies to chase down the player until they lose sight of them. This design pattern was useful for our project because it keeps separate code intended to run during certain Zombie states from overlapping with each other and running at the same time, and it also makes the code more readable to teammates who were not coding in the ZombieNPC class in case they want to add code to it. For example, I (Bilal) didn't code up the Zombie class and was able to look at the code and easily add code to play certain music depending what state the Zombies were in just by looking at the member variable and method names. In the RunWanderState(), I made code for regular background music to play and in the RunChaseState(), I made code for chase music to play.

Our third design pattern we used in our project is the Singleton Pattern for our Player class. We made our Player a Singleton because the game is singleplayer and only one player is needed in the scene at a time, and also so other classes can access the Player object if needed at all times. For example, in our Item class we access the Player Instance object in the OnMouseClick() method and use it to add the clicked Item's data into the Player's list member variable of ItemData components _inventory. Additionally, we access the Player Instance in the child class JoeDialogue in its overridden class CheckForQuestItem() to access the Player's inventory with a foreach loop and check to see if the Player has his Beans and if they do, Joe will show different dialogue to the Player. This pattern was useful in our project because it allows each class to have easy access to the Player class and use any of its members variables or methods if needed. If we didn't use this pattern, adding a clicked Item's data to the Player's inventory and having Joe check specifically for his Beans/Quest Item would have been much more difficult to implement in code as opposed to only having to use Player.Instance.player._inventory.Add(_data); and 
  foreach (ItemData item in Player.Instance.player._inventory) respectively to solve these problems quick and easily.
